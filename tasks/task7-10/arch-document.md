## Задание 8. Выявление и устранение «горячих» шардов

Для выявления горящих шардов в первую очередь необходимо добавить мониторинг.

### Предлагается использовать следующие метрики:

#### 1. Нагрузка на шарды

```js
// Количество операций на шардах
db.serverStatus().shardingStatistics.operationCount
{
  "insert": 15000,    # ➡️ Если на одном шарде в 10x больше
  "update": 8000,     # ➡️ Возможен hot shard
  "delete": 500,
  "query": 45000
}

# 1.2 Current Operations
db.currentOp(true).inprog.filter(op => op.shard)
```

#### 2. Использование ресурсов

```js
// Загрузка CPU
db.serverStatus().mem
db.serverStatus().cpu

// Обьем потребляемой памяти
db.serverStatus().mem
{
  "resident": 2048, // Использование RAM
  "virtual": 4096,
  "mapped": 1024
}

// Загрузка диска (запись/чтение данных)
db.serverStatus().opLatencies
{
  "reads": { "latency": 120, "ops": 15000 },
  "writes": { "latency": 85, "ops": 8000 }
}
```

#### 3. Количество чанков на шардах

```js
// Кол-во чанков по шардам
sh.status()
// Смотрим неравномерность:
// shard1: 150
// shard2: 45
// shard3: 148

// Jumbo Chunks (мониторинг частей данных, размер которых превышает максимальный)
db.adminCommand({ listsplits: "shop.orders" })

// Статистика миграции чанков
db.getSiblingDB("config").changelog.find({
  "what": "moveChunk.commit"
}).sort({ time: -1 }).limit(10)
```

#### 4. Производительность

```js
// Логировать долгие запросы (> 50ms)
db.setProfilingLevel(1, 50)
```

### Уведомления

Также для своевременного обнаружения горящих шардов предлагаю использовать уведомления.

### Методы устранения горячих шардов

#### Перебалансировка данных

```js
// Принудительная балансировка конкретной коллекции
sh.startBalancer();
sh.setBalancerState(true);

// Для конкретной коллекции
sh.disableBalancing("shop.orders");
sh.enableBalancing("shop.orders");

// Ручное перемещение чанков
db.adminCommand({
    moveChunk: "shop.orders",
    find: { geoZone: "EU", orderDate: ISODate("2023-12-01") },
    to: "shard2"
});
```

#### Оптимизация шард-ключа

```js
// Если текущий ключ не оптимален - меняем стратегию
// Пример: с Range на Hash для равномерности
db.adminCommand({
    refineCollectionShardKey: "shop.products",
    key: { _id: "hashed" }
});
```

#### Сегментация горячих данных
```js
// Для orders - создание зон для горячих регионов
sh.addShardToZone("shard-cold", "cold");
sh.addShardToZone("shard-hot-1", "hot");
sh.addShardToZone("shard-hot-2", "hot");

sh.updateZoneKeyRange("shop.orders",
    { geoZone: "US", orderDate: MinKey },
    { geoZone: "US", orderDate: MaxKey },
    "hot"
);
```

## Задание 10.1 Определите, какие части данных интернет-магазина (например, заказы, товары, корзины, история заказов, пользовательские сессии) являются критически важными с точки зрения целостности и скорости обработки

Данные по остаткам необходимо вынести в отдельную сущность, это поможет снизить нагрузку на основные таблицы и позволит использовать геошардирование для них, чтобы хранить данные по остаткам для каждой отдельной локации. Пересчеты остатков будут частыми, но мы не можем вынести их в Cassandra, так как Cassandra не соблюдает ACID и в ней отсуствуют атомарные операции, таким образом мы можем попасть в ситуацию когда мы спишем больше чем у нас есть.

Для корзины мы будем использовать Cassandra.

Так как мы ожидаем большую нагрузку и большое количество одновременных пользователей пользовательские сессии тоже необходимо вынеси в Cassandra.

  - Геозоны изолируют нагрузку по регионам
  - Равномерное распределение товаров

Решардинг:
  - Можно добавлять шарды для новых регионов
  - Минимальное перемещение данных при изменении топологии
  - Старые геозоны остаются на своих шардах

## Задание 10.3 Какие стратегии (Hinted Handoff, Read Repair, Anti-Entropy Repair) можно применить для обеспечения целостности данных?

Для регулярного поддержания здоровья узлов рекомендуется запускать инкрементальное восстановление (Anti-Entropy Repair) ежедневно, каждый вечер.

### Остатки

#### Стратегии

Read Repair

### Пример конфигурации

```js
// Стратегия: Write Concern + Read Concern
db.stock.updateOne(
    { productId: "078cab0d-51eb-4c36-b006-b40fdb17d407", geoZone: "RU", quantity: { $gte: 1 } },
    { $inc: { quantity: -1 } },
    { 
        writeConcern: { w: "majority", j: true },  // Журналирование
        readConcern: { level: "majority" }
    }
);
```

#### Обоснование

Требования_бизнеса:
  - Write Concern "majority": Гарантия записи на большинство нод
  - Journaling: Защита от потери данных при сбоях
  - Read Concern "majority": Чтение актуальных данных

Решения:
   - Hinted Handoff: Не используем так как есть риск продаж сверх имеющихся остатков при временной недоступности нод
   - Read Repair: Гарантированное исправление расхождений при каждом чтении

Риски:
  - Увеличенная задержка (latency) записи, но исключаем oversell
  - Лучше отклонить операцию, чем продать отсутствующий товар

### Корзины

#### Стратегии

Hinted Handoff + Read Repair

#### Пример конфигурации

```sql
CREATE TABLE carts (
    ...
) WITH 
    hinted_handoff_enabled = true,
    read_repair_chance = 0.1,         -- 10% вероятность
    dclocal_read_repair_chance = 0.2; -- 20% в датацентре
```

#### Обоснование

Требования:
  - Низкая задержка (latency) записи (добавление в корзину)
  - Высокая доступность при пиковой нагрузке
  - Допустима небольшая eventual consistency

Решения:
  - Hinted Handoff: Гарантирует запись даже при падении нод
  - Read Repair 10%: Баланс между консистентностью и производительностью

Риски:
  - Корзина может временно показывать старые данные
  - Принимаемый компромисс для производительности

#### Обоснование

### Пользовательские сессии
